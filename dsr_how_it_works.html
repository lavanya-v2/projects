Overview

The DSR Generator is an automated tool that pulls data from Jira every evening, analyses team activity using AI, and produces structured status reports for projects, accounts, and leadership. It eliminates manual report writing while providing consistent, auditable health signals.

Reports are generated automatically each evening (IST) via a scheduler. They can also be triggered manually from the dashboard at any time.

How Reports Are Generated

Each report generation follows a strict sequence of steps:

1
Fetch issues from Jira

All tickets from the project's active sprint (or updated in the last 2 days on Kanban boards) are fetched, including their full history, comments, and attachments.

2
Filter to team members only

Tickets are narrowed down to those assigned to registered team members — by email, Jira account ID, or name. Dev, QA, and UAT assignees are all checked.

3
Identify the report window

The tool determines the "report window" — the time since the last report was generated. Typically this is the previous day's report timestamp to today's report timestamp (approximately 24 hours, anchored to 6:30 PM IST).

4
Classify tickets: Active vs. Context

Active tickets had real activity in the window (status change, comment, attachment, or a GitHub/PR commit). These form the work summary. Context tickets are still in-flight but had no activity — they are passed to the AI as background only.

5
Calculate project health (deterministic)

A rules-based engine calculates health before the AI sees any data. This ensures health scores are consistent and explainable — not influenced by tone or word choice.

6
AI generates the narrative

Claude AI writes the executive summary, work summary, key risks, and plan for tomorrow — using only the active tickets as source of truth. The AI must honour the pre-calculated health score.

7
Save and publish

The report is saved to the database and made available in the dashboard. It can also be exported to Excel or PowerPoint.

Ticket Filtering Logic

Not every Jira ticket on the board makes it into the report. Here is the full filtering hierarchy:

Which tickets are included?

Check How it works
Team member match Main assignee, QA assignee, or UAT assignee must be a registered team member for the project. The tool does email-based and name-based matching to handle contractor IDs and email variants.
Activity within window At least one of: status change, comment, attachment, or GitHub/PR activity within the report window. Tickets with only a generic "link update" (e.g. a Jira auto-link) are excluded.
Sprint membership For Scrum projects, tickets must be in the active sprint. For Kanban projects, tickets updated within the last 2 days are considered.

Active vs. Context tickets

Type Definition Used in
Active Had specific activity (status change, comment, PR commit) in the report window Work summary, executive summary, plan for tomorrow
Context In-flight but no activity in the window — still in the sprint Passed to AI as background only, not cited as "work done"

Stale tickets

A ticket is flagged as stale if it has been in In Progress status for more than 3 days with no Jira updates AND no GitHub/PR commit activity. Stale tickets appear in the risks section but do not affect the health colour — they are a narrative signal only.

⚠️
A ticket won't appear in the report if it had activity today but the assignee is not a registered team member. If you notice missing tickets, first check team member registrations in the admin panel.

Project Health Scoring

Health is determined by a two-axis deterministic engine, not by the AI. The AI narrates what happened; the engine decides the colour. This keeps health consistent, auditable, and free from AI sentiment bias.

🔵 Axis 1 — Blocked Ticket %

What share of your WIP tickets are stuck? Measures the ratio of Blocked tickets vs. all tickets In Progress, In Review, QA, and UAT.

🟣 Axis 2 — Production Bug Score

How many active Bugs are in the sprint, and how critical are they? Accounts for bug count, priority level, and how recently the bug was created.

Each axis independently produces a Green, Amber, or Red signal. The two signals are then combined into the final project health.

Axis 1 — Blocked Ticket Percentage

WIP pool = tickets in: In Progress + In Review (Dev Complete / PR Review) + QA / Testing.
UAT tickets are excluded entirely — once a ticket reaches UAT, V2's development work is complete (only customer/PO sign-off remains). UAT can never contribute to blocked percentage.
Blocked % = number of Blocked tickets ÷ WIP pool size × 100.

Condition Result
Blocked % is ≥ Amber Threshold (default 20%) Amber
Blocked % is below the threshold Green
✅
A single blocked ticket will not turn a project Amber — unless the WIP pool has only 4 or fewer tickets total. For a typical 12-ticket project, you'd need 3 or more blocked tickets (25%) before the Amber threshold is reached.
ℹ️
The Amber Threshold (default 20%) is configurable per account in the database. Account managers can request a different threshold without any code changes.
✅
Why exclude UAT? V2 typically has one BA; UAT is run by the customer or Product Owner. Blocking a UAT ticket would unfairly penalise the team for a dependency that is entirely on the customer side.

Why this approach?

A blocked ticket often reflects an external dependency — a third party, a decision, or an environment issue — not a failure by the team. The threshold exists so one dependency blocker doesn't unfairly colour the whole project, but a pattern of multiple blocks does get flagged.

Sprint Burndown — QA Partial Credit

The sprint burndown uses weighted completion to avoid penalising teams whose work is late-stage but nearly done. A ticket in QA has already passed development and code review — it counts for 0.6 rather than 0.

Ticket Status Completion Weight Rationale
Done 1.0 Fully complete
UAT / PO Review 1.0 V2 work is done — awaiting customer sign-off only
QA / Testing 0.6 Development done, in final validation
In Review, In Progress, Blocked, etc. 0.0 Still in active development

completionPct = Σ(weights) / totalV2Tickets × 100

offTrackPct = sprintElapsedPct − completionPct

The health rationale for each daily report includes the QA count so the partial credit is transparent (e.g. "Sprint: 4 done + 2 in QA (0.6 credit) of 8 → 65% weighted completion").

ℹ️
Example: Sprint day 5 of 10 (50% elapsed). 8 tickets total: 3 Done + 3 in QA + 2 In Progress. Weighted completion = (3×1.0 + 3×0.6) / 8 = 60%. offTrackPct = 50 − 60 = −10% (actually ahead). Without partial credit it would show 3/8 = 37.5% → 12.5% behind pace.

Axis 2 — Production Bug Score

Only Jira tickets with issue type = Bug or Sub-bug where the environment is Production are counted. Only fresh bugs — created within the 15-day window relative to sprint start — are scored. Bugs outside that window are treated as intentionally planned and completely excluded.

ℹ️
The 15-day sprint-relative age rule:
  • Scrum: A bug created more than 15 days before the sprint start date is treated as a planned ticket. It is assumed the product team intentionally scheduled it into the sprint. Only bugs created within 15 days of sprint start (or after it started) are tracked.
  • Kanban: Same rule, but the reference point is the current week's Monday instead of a sprint start date.

Special cases (excluded from or adjusting the score)

Case Detection Effect
Old / planned bug Created > 15 days before sprint start Completely excluded — no score impact
Re-opened sub-bug Sub-bug whose parent story is still active on the board Not scored. AI mentions it as "re-opened" or "regression on [parent story]" in workSummary only.
Spillover bug Bug carried over from a previous sprint (Sprint changelog shows a prior sprint) Forces Axis 2 to at least Amber. Flagged as a Risk in the AI output.
Bug in UAT Status = UAT On plan — excluded from scoring.

⚠️
Volume-percentage rows (e.g., "bugs = 5–10% of active tickets") have been removed. Sprint backlog composition is the responsibility of the PO/Scrum Master — a high number of bugs on the board does not automatically mean V2 is at fault.

Final Health — The Balanced Combination

The two axis scores are combined using a rule designed so that neither signal dominates alone. Only when both axes are pointing amber — meaning there are both blocked tickets AND production bugs — does the project escalate to Red.

Axis 1 (Blocked %) Axis 2 (Prod Bugs) Final Health
Green Green 🟢 Green
Amber Green 🟡 Amber
Green Amber 🟡 Amber
Amber Amber 🔴 Red — both signals firing together
Any Red 🔴 Red
💡
A team with several blocked tickets but no bugs stays Amber, not Red. Equally, a team with one medium-priority bug and no blockers stays Amber. Red requires a combination of signals or an independently critical bug.

What about the AI?

The AI receives the pre-calculated health score and must use it as-is. The only exception: if the AI finds clear evidence of a P0 production outage or critical live incident in the ticket descriptions that was not captured by the rules engine, it may escalate from Amber to Red. It may never downgrade Red or Amber to a better colour.

Weekly Report Health — Majority Rule

The weekly project report health is derived from the daily health snapshots for the week using a majority rule. A single bad day no longer condemns the entire week.

Daily Breakdown Weekly Health Rationale
Strict majority (> 50%) of days are Red 🔴 Red More than half the working week was Red
Any Red or Amber day, but not strict majority Red 🟡 Amber Includes ties — e.g. 2 of 4 days Red → Amber
All days Green 🟢 Green Entirely clean week
💡
Example: Mon=Red, Tue=Green, Wed=Green, Thu=Green, Fri=Green → 1 of 5 days Red (20%, not a strict majority) → Amber. Previously this would have been Red under the old worst-day rule.

A weeklyHealthRationale string is stored alongside the weekly report and displayed as a small ⓘ tooltip next to the health chip in the Weekly Reports list. It shows the day-by-day breakdown and which rule applied.

Program-Level Reports

A Program is a named grouping of projects within a single account (a program never spans accounts). Programs are administered under Administration → Programs by admins/superusers, who assign projects and designate program owners. Program reports roll up the underlying project reports into one consolidated, leadership-ready view — the program equivalent of an account report, but scoped to just that program's projects.

📆 Weekly Program
🗓️ Monthly Program

What a program report contains

Each cadence pulls every active, non-shared project in the program, loads (or generates on the fly) that project's report for the period, and produces a single consolidated deck:

  • AI executive summary across all program projects
  • Key accomplishments and an explicit red-project list
  • Collated manager insights (rolled up from the project reports)
  • Consolidated risks and action items
  • An overall program health rating

How it works

AspectBehaviour
Weekly business week Weekly program reports enforce a Friday–Thursday week (start must be a Friday, end a Thursday, same calendar week). Legacy Sun–Sat reports cannot be regenerated.
Health Deterministic override using the program's redThresholdPercentage (falls back to the account threshold, else 30%). If red-project % ≥ threshold → Red; else any Red/Amber → Amber; else Green. The more severe of the AI verdict vs. the deterministic result wins.
Caching & queueing Reports are cached by (program, week/month, year). If none exists yet, the user is prompted to "Queue your request" — generation runs asynchronously on a background queue. A program with no projects returns an error.
Output format A downloadable PowerPoint (PPTX) deck, re-rendered from stored report data. Re-downloading never re-runs the AI — it rebuilds the file from the saved report.
Coverage tracking Each report records projectsIncluded and projectsMissing, so gaps in coverage are explicit rather than silent.
🔐
Visibility is owner-based, not account-inherited. Superusers and admins see all non-empty programs. Everyone else sees only programs where they are an explicit program owner (a program-scoped permission). Having access to the account does not grant visibility of that account's program reports.

Executive-Ready Summaries

All AI-generated executive summaries are written for senior leadership and CEOs who have no Jira access. The AI is explicitly instructed to describe work in functional and business themes only.

🚫
Ticket ID ban — Jira ticket IDs (e.g. PROJ-123) are never permitted in: Executive Summary, Key Risks, or Plan for Tomorrow / Executive Plan. Ticket IDs are only allowed in: Work Summary and the Ticket-Level Details section.

Praise-free rule — Generic morale statements are forbidden in all executive fields: "the team made excellent progress", "outstanding results", "strong velocity", "commendable effort". Every sentence must name a specific feature, module, capability, or factual delivery outcome.

What Summaries Look Like

❌ Rejected (ID or praise) ✅ Accepted (specific + factual)
"LOSAI-6066 deployment moved to Testing phase." "Payment integration advanced through testing, with document management component awaiting business sign-off."
"SC-1180 and SC-1181 completed and merged." "Authentication and session management improvements were completed and integrated."
"The team made excellent progress this week." "Loan origination module completed UAT; bulk upload feature passed QA and is pending deployment sign-off."
"Key Risk: LP-204 is blocked." (in keyRisks field) "Key Risk: Bulk export feature blocked pending third-party API credentials from vendor."
ℹ️
These rules apply at all report levels: daily, weekly project, and account weekly. The only exception is the Ticket-Level Details section (daily DSR only) where ticket IDs are explicitly required for traceability.

Health Rationale — Transparent ⓘ Tooltip

Every daily and weekly project report now shows a small ⓘ icon next to the health chip. Hovering it reveals the deterministic rationale — the exact numbers used to derive the colour — so health decisions are never opaque.

Daily Report Rationale

Stored in the health_rationale column of daily_board_snapshots. Example:

ℹ️
Health: Amber. Axis 1 (Blocked): 2/9 WIP (22.2%) ≥ 20% threshold → Amber. Axis 2 (Prod Bugs): 0 bugs → Green. Sprint: 4 done + 2 in QA (0.6 credit) of 10 → 52% weighted, 45% elapsed → 7% ahead. Final: Amber (one axis).

Weekly Report Rationale

Stored in weekly_health_rationale on project_weekly_reports. Example:

ℹ️
Week status: Amber. Daily: 2026-03-17=Green, 2026-03-18=Amber, 2026-03-19=Green, 2026-03-20=Green, 2026-03-21=Green. Rule: strict majority Red (>2 of 5 days) → Red; any Red/Amber day → Amber; all Green → Green.

The rationale is generated deterministically by the report engine (not by AI) and stored at report generation time. Older reports generated before this feature will not have the tooltip.

Ticket-Level Details (Daily DSR)

Daily reports include a collapsed Ticket-Level Details accordion that provides a one-line activity log for every ticket that had real work done that day. This is the only place Jira ticket IDs appear in a DSR — executive sections are always ID-free.

Format

📋
- LP-204: [Story] bulk export API completed, moved to QA - LP-211: [Bug] null pointer in loan calculator fixed, in Code Review - LP-198: [Task] infrastructure upgrade script tested successfully, Done

Rules

  • Only tickets with actual activity that day are listed (not backlog or context-only tickets)
  • One line per ticket: - KEY: [issuetype] brief description, current status
  • Maximum 15 words per line
  • Up to 15 tickets per report
  • Generated by AI and stored in the ticket_details column — collapsed by default in the UI
💡
The ticket details section is for operational traceability (delivery leads, project managers). The executive sections above it are for senior stakeholders who need business outcomes, not ticket numbers.

UAT Ticket Handling

UAT (User Acceptance Testing) tickets are treated as V2-team-complete across all health and delivery metrics. Specific rules:

  • Blocked axis: UAT tickets are excluded entirely from the WIP pool — they cannot contribute to blocked % regardless of assignee or status
  • Sprint burndown: UAT tickets count as 1.0 (fully done) — same weight as Done tickets
  • AI summaries: Many tickets at UAT near sprint end → AI notes sprint formal closure depends on customer sign-off (one sentence, schedule dependency framing only, never framed as a team failure)
  • UAT assigned to a V2 team member: Minor note in AI output only (proportional, does not affect health colour)

Trends

Trends is a cross-project, account/org-wide set of time-series charts (Recharts) showing how each project is trending over recent sprints. Pick an Account and a V2-only scope toggle; the view has its own sub-tab strip:

Sub-tabWhat it shows
Productivity SP-done vs SP-planned productivity % per project (throughput SP for Kanban). Each project shows current vs. average, a trend pill (up / down / flat + %), and a health dot: Green ≥ 80%, Amber 60–80%, Red < 60% delivery.
Defect Density Bugs per 100 SP over successive sprints.
Reopen Ratio Reopened stories ÷ total stories per sprint, with invalid-reopen exclusions.

Each chart surfaces the current value, the running average, the direction of travel, and a health band — so a manager can spot a project sliding over time, not just its snapshot today.

🔐
Trends is lead-or-above only. Unlike Board View, members are explicitly blocked from the Trends route — it is a cross-project, org-wide view intended for leads and managers.

Delivery Presentations

A customer-facing, slide-based executive delivery review built for a client meeting. It is generated per Account (optionally filtered to a single Program), rendered as an on-screen slide deck, and exported to a WYSIWYG PDF. It pulls live metrics, risks, action items, milestones, and trends; lets a manager curate and edit them; supports a live present mode with speaker notes; and captures Minutes of Meeting (MOM) afterwards. It lives under its own Presentation → Delivery Presentation nav section.

The 5-step build wizard

1
Basics & Scope

Title, meeting date, reporting window, overall health, project selection. Two scope modes: By Account (pick any of the account's projects) or By Program (the program's projects are auto-selected, whole-program). The window is either a free-form date range or a single completed sprint (single-project only).

2
Highlights & Risks

AI-generated executive summary + key highlights (achievements, blockers, capacity) and a risk list. The summary is AI-authored but editable — a refresh never overwrites an edited summary.

3
Action Items & Tech

Curated action items (project + program scope), tech recommendations, discussion points.

4
Per-Project Drilldown

Per-project narrative, health (computed, with manual override), sprint metrics, quality metrics, and per-developer team tables.

5
Additional Insights

Custom free-text / table sections plus milestones.

A Preview / Refresh re-pulls live metrics and additively merges action items (never overwriting edits). A "refresh needed" cue appears whenever the window or scope changes so the deck never goes stale.

The per-slide V2 ⇄ Whole-Team toggle

Scoped slides (Overview, Trends, each Drilldown) carry a compact V2 Team ⇄ Whole Team toggle; the deck defaults to Whole Team. Scope is tracked per slide, and the PDF reads the same map — so the export is WYSIWYG to exactly what was on screen.

Both scopes are precomputed on the backend from PerfTicketFact using the same formulas as Board View, so each scope reconciles to the board by construction. The toggle affects committed/delivered SP, capacity, reopens & reopen %, productivity %, spillover, scope-added (mid-sprint scope creep), removed/re-estimated SP, bug counts & density, team tables, and per-developer trends. Percentages are re-derived from each scope's own planned-SP denominator, so they always reconcile.

ℹ️
The toggle is hidden for Kanban/WSR drilldowns and older saved presentations that predate dual-scope data. Presenters can also manually override headline tile numbers per scope; overrides apply only to the top-level tiles, never to per-sprint tables, team tables, or trend charts.

Slides produced

  • Highlights, Risks & Actions (2×2 quadrant)
  • Trends (velocity / quality over the last 5 completed sprints)
  • Team Capacity (optional, hidden by default)
  • Additional Insights (paginated custom sections)
  • Per-Project Drilldown (one per project; includes a live "Current Sprint" in-flight card)

Present mode & Minutes of Meeting

The viewer has a review mode (internal — all controls: Edit, MOM, Manage Trends, Download PDF) and a clean present mode (customer-facing — controls hidden). During a presentation you can type presenter notes per slide; these feed MOM generation, which can be AI-drafted from a transcript + notes (capped at 3 regenerations), saved as a draft, then accepted. Presentations can also be duplicated/cloned, deleted, and locked.

🔐
Access: Superusers/admins have full access. Create/duplicate is limited to those, plus a manager/lead who has access to at least one selected project. In the list/view, non-privileged users only see presentations that include ≥1 project they can access. Note: unlike Program reports (PPTX), Delivery Presentations export to PDF only.

Excel / CSV-Driven Projects

Not every project is connected to Jira. A project's data source is set at creation to Jira, Azure DevOps, or Excel Upload. For an Excel project, work-item data is uploaded as a spreadsheet each reporting period instead of being pulled from Jira — but from there it flows through the exact same health engine and report pipeline.

Step 1 — Onboarding & column mapping (once)

When an admin creates the project with Source = "Excel Upload", they upload a sample spreadsheet. Its header row is read in the browser, and the admin maps each of the app's canonical fields to a column from the sample. This is how arbitrary customer headers ("Ticket #", "Owner", "State"…) are translated to the app's internal fields.

Canonical fieldRequired?
External ID, Title, Type, Status, Assignee Email, Created Date, Last Updated Required (all templates)
Sprint Name, Sprint Start Date, Sprint End DateRequired for Scrum-style projects
Priority, Story Points (or Estimated Hours), Parent/Epic, Labels, Done Date, Status Changed On Optional

The mapping is stored in a dedicated template_mappings table (one row per project), which the project points to. At upload time the validator uses "use the mapped customer header if present, else fall back to the canonical default header" — the single translation seam for the whole feature.

ℹ️
A project also carries a reporting frequency (Daily or Sprint). Daily projects produce daily DSRs on each upload; Sprint projects feed the Excel Sprint Board in Team Performance instead.

Step 2 — Upload period data (each period)

From the Data Imports page, the user picks the account and Excel project, optionally downloads a pre-formatted template (built-in scrum or kanban), chooses a report date (or relies on the sprint columns), and selects a file.

  • Formats: .xlsx, .xls, and .csv (the picker offers .xlsx / .csv); 20 MB limit. CSV is reshaped through the identical validation path.
  • Optional "Status History" sheet (External ID, From/To Status, Changed On, Changed By) unlocks full-fidelity cycle-time and reopen metrics; without it, metrics run in "approximate" fidelity.

Step 3 — Validation (before anything is saved)

Every upload is validated as a dry run first — no data is written until you confirm. A two-pass check runs strict, then falls back to best-effort with fuzzier coercion:

  • Required headers per template must be present; header matching is fuzzy (case, spacing, punctuation).
  • Per row: External ID, Title, Status, Created Date, Last Updated are required.
  • Type is normalised to Story / Task / Bug / Spike / Epic / Sub-task (aliases like "defect" → Bug handled).
  • Duplicate External IDs are rejected. Dates accept real dates, Excel serial numbers, or parseable strings.

The UI shows the validation status, the mode used (strict / best-effort), row and history counts, and tables of any errors and coercions to review. Confirm & Import is enabled only when validation passes.

Step 4 — Report generation (same engine as Jira)

On confirm, the upload is persisted (imports, work items, status history, and any sprints found in the rows). Reports always read the latest applied import, so re-uploading the same period supersedes the previous snapshot. Behind the scenes each Excel row is reshaped into the same internal "issue" envelope that Jira issues use — including a synthesised change history — so blocked-today detection, activity gating, and the two-axis health engine all run identically. A daily or weekly upload automatically queues the standard DSR generation job; the resulting report appears on the Daily Reports page just like a Jira project's.

💡
Because the data is normalised to the Jira shape immediately after upload, everything else in this guide — filtering, health scoring, executive summaries, Team Performance — applies to Excel projects unchanged. The only difference is where the raw data comes from.

Manager Insights

A layered annotation system lets team leads and managers add human context that Jira data alone cannot capture — escalations, customer concerns, verbal feedback, or any situation-specific commentary.

↓ AI collates all daily insights during WSR generation
🤖 Weekly Project (AI-collated)
Concise summary of the week's daily insights — editable after generation
↓ AI collates all project insights during Account WSR generation

How Insights Influence Executive Summaries

At weekly and account levels, if manager insights are present when the report is generated, they are incorporated into the executive summary in the same AI call — not as a post-processing patch. This means the summary is written with full awareness of the human context from day one.

💡
If a manager edits their insights after a report has been generated, a Preview → Accept flow lets them review a side-by-side diff of the old and proposed executive summary before committing the change.

Frequently Asked Questions

Why is my project showing Amber when we only have one blocked ticket?

One blocked ticket alone won't trigger Amber unless your total WIP pool is very small (4 or fewer tickets). If you see Amber with one blocked ticket, check whether there are also active production bugs in the sprint — the combination of both signals can cause escalation.

Why didn't my ticket appear in today's report?

The most common reasons: (1) the assignee is not registered as a team member for the project, (2) the ticket had no qualifying activity in the report window — a comment or status change is needed, (3) the ticket is in Done status and was filtered out.

What counts as a "production bug" for health scoring?

Only Jira tickets where the Issue Type is set to Bug. The tool does not scan ticket titles or descriptions for the word "bug". If a bug is logged as a Story or Task it won't count toward the bug score — but you should raise it as a Bug type in Jira for accurate reporting.

Can the Amber threshold be changed for our account?

Yes. The threshold (default 20%) is stored per account in the database. Contact your admin or delivery manager to update it. No code changes or deployments are needed.

The report says "No Activity Found" — why?

This means no team tickets had qualifying activity (status change, comment, or PR commit) within the report window. This usually happens on holidays, or if work was done but not logged in Jira. The report window is typically from the previous evening's report up to the current report time.

How are weekend activities handled?

If a ticket has activity on a Saturday or Sunday (IST), it is flagged as "Weekend Activity" and explicitly called out in the Executive Summary. This gives visibility to efforts made outside regular working hours.

Why do UAT tickets count toward delivery % in Team Performance?

UAT (User Acceptance Testing) is the customer's or Product Owner's responsibility. When a ticket reaches UAT, V2's development work is complete. Counting UAT as done accurately reflects the team's delivery. Sprint formal closure may still depend on the customer signing off — this is treated as a schedule dependency, not a team failure.

My Kanban project shows no sprints in Team Performance — is that normal?

Yes. Kanban projects have no sprint structure by design. In the Team History tab, Kanban projects show the date-range velocity view instead: pick a start and end date, choose a period slice duration (e.g. 15 days), and the system calculates how many tickets each developer delivered in each slice.

What does "spillover" mean in the Sprint Report?

Spillover tickets were in the sprint at its start but did not reach Done by the sprint end date — they carry over to the next sprint. A high spillover count is a leading indicator that commitment sizing may need adjustment.

Why is my project Amber even though most of the week was Green?

The weekly health uses a majority rule: only a strict majority (> 50%) of days need to be Red for the week to turn Red. Any single Red or Amber day is enough to make the week Amber. Hover the ⓘ icon next to the health chip to see the full day-by-day breakdown.

Why does the health colour change when I regenerate a report?

Health is recalculated from live Jira data at generation time. If tickets were moved, bugs were resolved, or QA work was completed since the last generation, the new calculation will reflect those changes. The ⓘ tooltip shows the exact numbers used so you can see what changed.

Where can I see ticket IDs for today's work?

Open any daily report and expand the Ticket-Level Details accordion (collapsed by default below the Detailed Work Summary). It shows a per-ticket log with Jira IDs, issue types, and a one-line description of what was done. Executive sections above it are always ID-free.

Why does my QA work improve the sprint burndown differently from In Progress work?

A ticket in QA receives 0.6 weighted credit (versus 0 for In Progress). This reflects that QA work is near-complete — development and code review are done, only testing remains. This prevents a sprint full of late-stage QA work from looking falsely behind pace. The health rationale tooltip shows the QA count and partial credit calculation.

I have access to the account — why can't I see its program report?

Program report visibility is owner-based, not account-inherited. Only superusers, admins, and users who are explicitly designated program owners can see a program's reports. Ask an admin to add you as an owner of that program.

Why does the Delivery Presentation default to "Whole Team"?

Customer meetings usually discuss the entire delivery, so the deck defaults to Whole Team. Every scoped slide has a V2 Team ⇄ Whole Team toggle, tracked per slide, and the PDF exports exactly what is on screen. Both scopes are precomputed from the same performance data as the Board View, so the numbers always reconcile.

How do I report on a project that isn't in Jira?

Create the project with Source = Excel Upload and map your spreadsheet's columns to the app's canonical fields once. Then upload a work-item file (.xlsx or .csv) each period from the Data Imports page. After validation, the data runs through the same health engine and report pipeline as a Jira project — see Excel / CSV Projects.

I'm a lead — why can't I close a risk?

By design, leads cannot mark a risk as Done. Managers, admins, and superusers can close risks; leads can create, comment on, and move risks between the active lanes (which requires a comment), but closing is reserved for higher roles.

What's the difference between an Action Item and a Risk?

An action item is a concrete to-do with an owner, due date, and Open→In-Progress→ Closed/Discarded lifecycle, tracked in a table across Project / Program / Account scopes. A risk is a potential problem being tracked and mitigated on a drag-and-drop board, with priority, source, mitigation plans, and a resolution on close. Use an action item for "someone must do X"; use a risk for "X might go wrong."

Why can't members open the Trends tab in Team Performance?

Trends is a cross-project, org-wide view intended for leads and managers, so members are blocked from it. Members can still open Board View read-only to see a single project's sprint scoreboard.
