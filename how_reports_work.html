The Big Picture

What This System Does

Think of this system as a smart assistant that:

  • Reads your Jira boards every day and writes daily status reports automatically
  • Understands what each team member is working on by filtering Jira activity within a 24-hour window
  • Calculates project health deterministically (rule-based, not AI opinion)
  • Summarises weekly, monthly, and account-level progress using Claude AI (Sonnet model)
  • Combines multiple projects into executive summaries and generates PowerPoint + Excel deliverables
  • Guards against AI hallucinations through a 4-layer defence system

Daily Status Report

What It Answers

"What did the team accomplish today? What's blocked? What's next?"

How It Works (In Plain English)

1
Fetch Tickets from Jira

Fetches all tickets from active sprint (Scrum) or recently updated tickets (Kanban), including full changelog, comments, attachments, and GitHub/PR activity.

2
Filter by Team Members

Only tickets assigned to registered team members (Main/QA/UAT assignees). Smart matching handles email variations and contractor accounts.

3
Determine Report Window

Calculate time window: Yesterday 6:30 PM IST → Today 6:30 PM IST (typically 24-hour window).

4
Classify Ticket Activity

Scan each ticket for activity within window. Classify as Active (had work), Context (no work), Blocked, or Stale. See detailed breakdown below.

5
Calculate Health Score

Math-based rules count blocked tickets (>3 days) and production bugs. Applies thresholds to determine Green, Amber, or Red status.

6
AI Writes the Summary

Claude AI reads active tickets and writes human-readable report. Summarizes work done, groups related tasks, identifies risks, suggests tomorrow's focus. Cannot override health score.

7
Validate AI Output

TemporalValidator scans for invented time durations. Logs warnings if hallucinations detected.

8
Save to Database

Complete report stored with metadata, ready for weekly rollup and historical analysis.

Detailed: How Ticket Activity is Determined

This is the most critical logic in the entire system. It determines which tickets appear in the "work done today" section versus "background context". All higher-level reports depend on this accuracy.

Step 1: Fetch Tickets from Jira

Board Type What Gets Fetched
Scrum All tickets in the active sprint + any tickets updated in last 2 days
Kanban All tickets not in "Done" status + any tickets updated in last 1 day

Step 2: Filter by Team Members

Only tickets assigned to registered team members are included. The system checks three assignee fields:

  • Main Assignee - Primary person working on the ticket
  • QA Assignee (customfield_10440) - Person testing the ticket
  • UAT Assignee (customfield_10441) - Person doing user acceptance testing
💡
Smart Matching: The system matches team members by email, Jira account ID, and name. It handles email variations like "aditya.bhoir@myccmortgage.com" vs "Aditya.Bhoir_EXT@myccmortgage.com" by comparing base email parts.

Step 3: Classify Each Ticket (Active vs Context vs Blocked vs Stale)

Report Window: Typically from yesterday 6:30 PM IST to today 6:30 PM IST

Active Tickets (Work Done Today)

A ticket is marked ACTIVE if ANY of these activities occurred within the report window:

Activity Type How Detected Example
Status Change Jira changelog shows status field changed "Moved from In Progress → Testing"
Comment Added New comment created in report window "Developer added update: Fixed bug in payment module"
Attachment Added Jira changelog shows attachment field changed "Screenshot.png attached"
Ticket Created Ticket creation date falls in window "New ticket created today"
GitHub/PR Activity Development field shows commit/PR in window "PR merged" or "Commit pushed"
Custom Field Update Any custom field changed (deployment, branch, etc.) "Deployment field updated"
ℹ️
Last Resort Check: For tickets in development statuses (In Progress, Code Review, Testing) with NO Jira activity, the system checks GitHub/PR commits as a fallback. This ensures work isn't missed when developers commit code but forget to update Jira.
Context Tickets (Background/Idle)

A ticket is marked CONTEXT if:

  • It's in the sprint/board (so relevant to the project)
  • BUT it had NO activity in the report window
  • Example: A ticket stuck in "Waiting for Approval" with no updates

How Context Tickets are Used:

  • Passed to AI as background information only
  • NOT mentioned in "work done today"
  • Help AI understand project context and dependencies
Blocked Tickets

A ticket is marked BLOCKED if:

  • Current status matches configured blocked statuses (typically "Blocked", "On Hold")
  • OR ticket moved to blocked status today (even if later unblocked)

Special Handling:

  • System tracks when ticket first became blocked (from changelog)
  • Calculates days blocked: Today - First Blocked Date
  • Only tickets blocked >3 days impact health score (prevents false alarms)
  • UAT tickets are excluded entirely from the WIP pool — once a ticket reaches UAT, V2's development work is complete. UAT tickets can never contribute to blocked %, regardless of status or assignee
Stale Tickets

A ticket is marked STALE if ALL of these are true:

  • Status is "In Progress" (or equivalent)
  • Last Jira update was >3 days ago
  • NO GitHub/PR activity in last 3 days (checked as fallback)
⚠️
Why Stale Detection Matters: Stale tickets indicate work that may be abandoned, blocked without proper status, or forgotten. They appear in the risks section but don't directly affect health color (only blocked tickets do).

Step 4: Production Bug Classification

Production bugs receive special handling for health calculations. The 15-day sprint-relative rule determines what is "fresh" vs "planned":

Bug Criteria Classification Health Impact
Issue Type = "Bug"/"Sub-bug" AND Environment = "Production" AND created within 15 days of sprint start Fresh Production Bug ✅ Scored (count + priority rules)
Bug created >15 days before sprint start date (Scrum) or week Monday (Kanban) Old Bug (Planned Work) ❌ Completely excluded
Sub-bug whose parent story is still active on the board Re-opened Story ❌ Not scored. AI mentions as "re-opened" in workSummary only.
Bug carried over from a previous sprint (Sprint changelog shows prior sprint) Spillover Bug ⚠️ Forces Axis 2 to at least Amber. Flagged as Risk in AI output.
Bug in "Done", "Resolved", "Closed", or "UAT" status Resolved / On-Plan Bug ❌ Not Counted
ℹ️
Why sprint-start-relative, not today-relative? The product team decides what enters the sprint. A bug created before the sprint preparation window (15 days before sprint start) was intentionally planned — it should not penalise the project. Only genuinely new incidents raised during or just before the sprint are tracked.

Health Calculation Rules

┌─────────────────────────────────────────────────┐
│           HEALTH CALCULATION RULES              │
├─────────────────────────────────────────────────┤
│                                                 │
│  AXIS 1 — BLOCKED TICKETS:                      │
│  - WIP pool = In Progress + In Review + QA      │
│    (UAT excluded — V2 work is done at UAT)      │
│  - Blocked % = blocked ÷ WIP pool × 100         │
│  - If ≥ 20% blocked → Amber                     │
│                                                 │
│  AXIS 2 — PRODUCTION BUGS (revised):            │
│  - Only fresh bugs (within 15d of sprint start) │
│  - Re-opened sub-bugs: noted in AI, not scored  │
│  - Spillover bugs: at least Amber + Risk flag   │
│  - Scored by count and priority (no % volume)   │
│  - 1 High/Critical → Red; 2+ High/Critical → Red│
│                                                 │
│  SPRINT BURNDOWN:                               │
│  - Done/UAT = 1.0 credit                        │
│  - QA / Testing = 0.6 credit (nearly done)      │
│  - Others = 0 credit                            │
│  - offTrackPct = elapsed% - weighted done%      │
│                                                 │
│  FINAL SCORE:                                   │
│  - Green:  Both axes Green                      │
│  - Amber:  One axis Amber                       │
│  - Red:    Both axes Amber, or bug score Red    │
│                                                 │
└─────────────────────────────────────────────────┘
ℹ️
This health score is deterministic (rule-based), not AI opinion. A ⓘ tooltip next to the health chip shows the exact numbers used — blocked %, bug score, sprint burndown — so the colour is always explainable.

Weekly Project Report

What It Answers

"How did the project perform this week? What got delivered? What are ongoing risks?"

How It Works

1
Date Validation

Start date must be a Sunday or Monday. End date must be a Friday or Saturday. Both dates must fall within the same calendar week. Duration cannot exceed 7 days. These rules prevent cross-week data mixing.

2
Cache Check

If a weekly report already exists in the database for this project + week number, it is returned immediately (forceRefresh: false). Generation only runs when explicitly requested via the "Queue" option.

3
Gather the Week's Daily Snapshots

Fetches all DailyBoardSnapshot records for this project within the date range. If none exist, generation is skipped (returns null — no empty reports created).

4
Calculate 3-Week Trend Context

Computes quantitative metrics for the current week, previous week, and two weeks ago: average active tickets, max blocked tickets, and throughput (tickets moved to Done). This context is passed to AI so it can make data-driven trend observations.

5
Analyze Blocked Tickets with Verified Durations

BlockedTicketAnalyzer scans 30 days of daily snapshots and calculates exact consecutive days blocked for each ticket. This data is passed directly to AI — the AI is forbidden from estimating or inventing durations.

6
Calculate Weekly Health (Majority Rule)

Weekly health is derived from the daily snapshots using a majority rule — not worst-day. Strict majority (> 50%) of days Red → Red. Any Red/Amber day → Amber. All Green → Green. A weeklyHealthRationale is stored with the day-by-day breakdown and shown as an ⓘ tooltip in the UI.

7
AI Aggregates the Week

Receives: daily summaries, 3-week trend metrics, previous 2 weeks' context, lane configuration, and verified blocked ticket durations. Produces: executive_summary (no IDs, no praise), work_summary, achievements (no IDs), risks, status, trendAnalysis, additional_notes.

8
Validate AI Output

TemporalValidator scans for suspicious phrases like "three consecutive weeks", "several weeks", "blocked for months". Logs warnings for human review.

9
Save Weekly Report

Upserts into project_weekly_reports. Stores executiveSummary, workSummary, achievements, risks, status, weeklyHealthRationale, teamMembers, and raw metrics.

What AI Receives (Inputs)

InputSourcePurpose
Daily summaries (Mon–Sat)DailyBoardSnapshot.workSummary, risks, healthCore content for the week
Current week metricsCalculated from snapshotsAvg active tickets, max blocked, throughput
Previous 2 weeks contextProjectWeeklyReport (last 2 weeks)Trend awareness (health, bug presence)
Trend context (3 weeks)DailyBoardSnapshot aggregationAI can compare velocity week-over-week
Blocked ticket durationsBlockedTicketAnalyzer (30-day scan)Verified durations only — no guessing

⚠️
Verified Durations: The system provides AI with mathematically calculated durations from historical data. If a project has no "Production" lane configured, the AI is explicitly instructed not to comment on production deployment throughput.

Weekly Account Report

What It Answers

"How is the entire account doing? Which projects need attention? What should executives know?"

How It Works

1
Gather All Project Weekly Reports

For an account like "CCMH", collects weekly reports from ALL projects (e.g., LS, LOT, LOWA, EXP, Secondary, LOSAI).

2
Identify High-Risk Projects

Reviews each project's health status. Calculates account health: If red projects ≥ 30% → Account RED; else if any red OR amber → Account AMBER; else → Account GREEN.

3
AI Synthesizes Account-Level Summary

Writes executive summary for entire account, lists key accomplishments across projects, identifies systemic risks, recommends action items. Must copy exact temporal language from project reports.

4
Validate Account Report

Extra validation for executive reports: checks each risk description, verifies durations against source project reports, flags mismatches for review.

5
Generate PowerPoint & Excel

Creates executive-ready files: PPT with cover slide, executive summary, achievements, risk matrix, health dashboard, action items. Excel with detailed metrics and trend analysis.

6
Save to Database

Stores complete account report with file paths to PPT/Excel deliverables.

Account Health Example

Health Summary:
├── LS: Amber (2 blocked items, 2 prod bugs)
├── LOT: Red (production defects, vendor impact)
├── LOWA: Amber (velocity down 30%)
├── EXP: Amber (3 blocked tickets)
├── Secondary: Amber (critical bug)
└── LOSAI: Amber (API blocked)

Red Projects: 1 (LOT)
Amber Projects: 5
Green Projects: 0

Calculation:
1/6 = 16.7% red (below 30% threshold)
But 5 amber projects exist
→ Account Health = AMBER

Monthly Project Report

What It Answers

"How did the project perform over the entire month? What are the trends?"

How It Works

Collects all weekly reports from the month (typically 4 weeks). AI aggregates to write monthly executive summary, highlight biggest achievements, identify persistent or recurring risks, and assess overall monthly health.

ℹ️
Temporal Accuracy: The system tracks when risks occur across weeks rather than adding up durations. For example: "Blocker appeared in weeks 1 and 3" rather than misleading statements like "blocked for 4 days total".

Shared Team Reports

What It Answers

"What did our shared / cross-functional team members accomplish across all the projects they worked on today?"

Some developers work across multiple projects simultaneously. A standard daily report only covers one project at a time. The Shared Team Report consolidates activity for a named group of people across every project they touched.

How It Works

1
Identify Team Members

A shared team is defined by a list of member names. The system locates each member's activity across all project daily snapshots for the target date.

2
Aggregate Project Reports

Collects the relevant sections (work summary, risks, plan) from each project's daily report where these members had activity. Combines them into one aggregated text block.

3
AI Consolidates the View

Claude receives the aggregated project reports and member list. It synthesises a single coherent daily summary: what the shared team accomplished across all projects, any cross-project risks, and a unified plan for tomorrow. Groups by project or theme, whichever is clearer.

4
Same Output Format as Daily Report

Returns health, executiveSummary, keyRisks, executivePlan, planForTomorrow, risks, notes, and workSummary — identical structure to a standard daily report.

ℹ️
Anti-Hallucination: AI is instructed not to mention tickets or work that were not in the aggregated reports, and to ignore "No activity" entries unless they are the only source available.

Team Performance Analytics

What It Answers

"How is each developer delivering across sprints? Who is consistently hitting their commitments? How is velocity trending over time?"

The Team Performance module provides on-demand sprint-level and historical delivery metrics per developer. It is separate from the automated daily/weekly pipeline — you select the project, sprint(s), and team members manually to generate a snapshot.

Tab 0 — Sprint Report

Select a closed or active sprint and one or more team members to generate a per-sprint breakdown:

SectionWhat it shows
Summary cards Total SP planned, SP done, overall delivery %, total spillover count
Sprint progress bar Percentage of the sprint window elapsed vs. work completed — useful for mid-sprint checks
Member table Per-developer: SP planned / SP done / delivery % / pipeline breakdown chips (In Progress, QA, UAT, Done)
Late QA movers Tickets that moved into QA after the sprint midpoint — potential at-risk items for sprint closure
Scope changes Tickets added or removed after the sprint start date
ℹ️
Delivery % definition: Story points in Done + UAT + QA statuses ÷ total story points assigned. Tickets at UAT count as V2-team-complete — development work is done, only customer/PO sign-off remains.

Tab 1 — Team History (Scrum Projects)

Shows a developer-card grid covering the last 3 closed sprints plus the current active sprint per member:

  • Bar chart per card: Planned SP vs. Done SP side-by-side for each closed sprint. Bars are colour-coded green (>=80%), amber (50–79%), or red (<50%) by delivery %.
  • Tooltip: Hovering a bar shows the full sprint name and delivery percentage.
  • Current sprint tile: SP done / SP planned so far, delivery %, and live pipeline breakdown (In Progress, QA, UAT, Done counts).

Tab 1 — Team History (Kanban Projects)

Kanban projects have no sprints, so Team History shows a custom date-range velocity view instead:

ControlWhat it does
Start date / End date Define the overall analysis window (default: last 90 days)
Period slice (days) Break the window into equal N-day periods (e.g. 15 days → six 15-day buckets from a 90-day range)

Each developer card shows:

  • Bar chart: Number of tickets delivered (moved to Done) per period
  • Average velocity: Avg tickets per period and avg story points per period across all slices
  • Current open tickets: Live breakdown of work in flight — In Progress, QA, UAT, Done counts
💡
Kanban history is calculated from Jira's "statusCategory changed to Done DURING (start, end)" JQL — one query per period slice. This gives accurate delivery counts even if tickets were later reopened or moved back.

UAT in Delivery Metrics

UAT (User Acceptance Testing) receives special treatment in all Team Performance calculations:

SituationHow it's reported
Ticket at UAT, assignee is the customer or PO Counted as V2-team-complete. Development work is done; not flagged as a risk against the team.
Many tickets at UAT near sprint end date AI may include one brief sentence noting sprint formal closure depends on customer/PO sign-off — framed as a schedule dependency, not a team shortcoming.
UAT ticket assigned to a V2 team member Flagged as a minor concern since UAT is normally customer responsibility. Proportional — not used to change health rating.

Executive-Ready Summaries

All AI-generated executive summaries are written for senior leadership and CEOs who have no access to Jira. Ticket IDs and raw ticket titles are meaningless to this audience — so the AI is explicitly instructed to describe work in functional and business themes only.

🚫
Ticket ID ban — Jira ticket IDs are never permitted in: Executive Summary, Key Risks, or Plan for Tomorrow / Executive Plan. IDs are only allowed in Work Summary and the Ticket-Level Details section.

Praise-free rule — Generic morale statements are forbidden across all executive fields: "excellent progress", "outstanding results", "strong velocity", "commendable effort". Every sentence must name a specific feature, module, or factual delivery outcome.

Before vs. After

❌ Rejected ✅ Accepted
"LOSAI-6066 deployment moved to Testing. LOSAI-6074 advanced to UAT." "Payment integration features advanced through QA into UAT, with one component awaiting business sign-off."
"SC-1180 and SC-1181 completed and merged to main." "Authentication and session management improvements were completed and merged."
"The team made excellent progress and delivered outstanding results this week." "Loan origination module completed UAT; bulk upload feature passed QA and is pending deployment sign-off."
"Key Risk: LP-204 is blocked." (in keyRisks) "Bulk export feature is blocked pending third-party API credentials from the external vendor."

Where Ticket IDs Are Allowed

Ticket IDs are permitted — and required — in the Ticket-Level Details section of daily reports. This is a separate collapsed accordion for operational traceability, distinct from the executive fields above it.

ℹ️
These rules apply at all report levels: daily, weekly project, and account weekly. The Ticket-Level Details section (daily DSR only) is the designated place for Jira ID traceability.

AI Methods

The AIService class has seven distinct methods — four generation methods and three insight collation methods:

1 · analyzeBoard() — Daily Report
Inputs: Active tickets (with daily activity), context/backlog tickets (up to 50), blocked tickets with last comment, stale tickets (>3 days in progress), previous day's snapshot, weekend activity highlights, lane configuration, pre-calculated health + rationale.

Outputs: health, executiveSummary, keyRisks, executivePlan, planForTomorrow, risks, notes, workSummary.

Key rules: AI cannot lower the pre-calculated health score (may only escalate to Red for P0 production outages). No percentage symbols in executiveSummary. No invented time durations. Only active tickets are described as having work done today.
2 · generateWeeklySummary() — Weekly Report
Inputs: Daily summaries for the week, previous 2 weeks' context (health + bugs), 3-week quantitative trend (avg active, max blocked, throughput), verified blocked ticket durations (from BlockedTicketAnalyzer), lane configuration.

Outputs: executive_summary (two paragraphs: achievements then risks), work_summary, achievements, risks, status, trendAnalysis, additional_notes.

Key rules: Blocked ticket durations must come verbatim from the verified data (format: "Ticket X blocked for 2 days (since 2026-02-20)"). If no Production lane is configured, AI must not comment on production deployment throughput. Sparse data → Green status, not Red/Amber.
3 · generateAccountSummary() — Account Weekly Report
Inputs: All project weekly summaries (name, summary, risks, status, high-severity-bug flag). Health is pre-calculated deterministically: ≥30% red projects → Account Red; any red or amber → Account Amber; else Green. Threshold is 30% by default.

Outputs: summary, key_accomplishments[], risks{summary, items[]}, action_items[], red_projects[], recommendations, health, notes.

Key rules: No Jira ticket keys in output. Projects with Unknown status are ignored — they do not contribute to health or risk narrative (absence of data is NOT a health indicator). Exact temporal language must be copied from project reports, never extrapolated.
4 · generateMonthlySummary() — Monthly Report
Inputs: All weekly report summaries for the month (week number, work_summary, achievements, risks, status).

Outputs: work_summary, achievements, risks, status.

Key rules: Blocked ticket durations must not be aggregated. If a ticket was blocked in week 1 and week 3, the output should say "recurring blocker in weeks 1 and 3" — NOT "blocked for 3 weeks total". Only patterns explicitly documented across multiple weeks may be called recurring.
5 · collateWeeklyInsights() — Manager Insights Collation
Inputs: Array of daily manager insight strings for the week, project name.

Outputs: A concise 2–4 sentence narrative summarising the human context themes across the week.

When called: Automatically during generateWeeklyReport() if any daily snapshots have managerInsights set. The result is passed to generateWeeklySummary() and stored in ProjectWeeklyReport.managerInsights.
6 · collateAccountInsights() — Account Insights Collation
Inputs: Array of { projectName, insights } objects for each project that has weekly manager insights.

Outputs: An account-level narrative that synthesises cross-project themes.

When called: Automatically during account WSR generation if any project weekly reports have managerInsights. The result is passed to generateAccountSummary() and stored in AccountWeeklyReport.managerInsights.
7 · refreshExecutiveSummary() — Post-Edit Refresh
Inputs: Report type, project/account name, stored work summary, health, existing risks, and updated manager insights.

Outputs: A refreshed executive summary string incorporating the new insights.

When called: On the POST /insights/preview endpoint when a manager edits insights after a report has already been generated. Returns both the old and new summary so the UI can show a diff. The update is only committed when the manager hits Accept.

JSON Parsing & Repair

AI responses are parsed as raw JSON. If parsing fails (e.g. truncated response), the system attempts repair heuristics in sequence: append "}, "}, etc. If all repairs fail, a fallback error object is returned and the raw response is written to error_analysis.log for debugging. This means reports always return a valid structure even when the AI model has issues.

Quality Assurance System

The 4-Layer Defense System

To ensure accuracy and prevent AI from inventing facts, the system uses multiple layers of verification:

Layer 1: Historical Data Analysis
BlockedTicketAnalyzer scans 30 days of reports and calculates exact blocked durations mathematically. Example output: "LS-1844: 2 days (since Feb 20)" based on actual historical data, not estimates.
Layer 2: Strict AI Instructions
AI receives explicit rules: "Use ONLY verified durations. NEVER say 'three weeks' unless it's in the data. FORBIDDEN phrases: 'several weeks', 'consecutive weeks'". This constrains the AI to factual statements only.
Layer 3: Post-Processing Validation
TemporalValidator scans AI output for suspicious phrases like "three consecutive weeks" or vague terms like "several weeks". When detected, warnings are logged for human review.
Layer 4: Monitoring & Alerts
DevOps team monitors application logs for validation warnings, reviews flagged reports, regenerates if needed, and continuously improves AI prompts based on observed patterns.

For Managers: What This Means for You

✅ What You Can Trust

Green/Amber/Red Health Scores:

  • Based on mathematical rules
  • Counts actual blocked tickets and bugs
  • Not AI opinion - it's calculated

Metrics (Numbers):

  • Average active tickets
  • Throughput (completed work)
  • Team member counts
  • All calculated from real data

Temporal Claims:

  • ✅ "Blocked for 2 days (since Feb 20)" ← Fact-checked
  • ✅ "Currently blocked" ← Safe statement
  • ✅ "Stale (>3 days)" ← Rule-based threshold

Health Explainability (new):

  • Hover the ⓘ icon next to any daily health chip → exact numbers: blocked %, bug score, sprint burndown
  • Hover the ⓘ icon next to any weekly health chip → day-by-day breakdown + majority rule applied
  • No more "why is this Amber?" — the reasoning is always one hover away

Ticket-Level Details (new, daily DSR):

  • Open any daily DSR → expand the Ticket-Level Details accordion (collapsed by default)
  • Shows one line per active ticket: ID, issue type, what was done that day, current status
  • This is the only place Jira IDs appear — all executive fields are always ID-free

⚠️ What to Verify

Qualitative Statements:

  • "Potential quality issues" ← AI interpretation
  • "Suggests systemic gaps" ← AI inference
  • These are helpful but should be investigated

If You See Warning Flags:

  • Check application logs
  • Regenerate the report
  • Compare with source data

📝 Adding Manager Insights

Each report has a Manager Insights card below the Executive Summary. Use it to add context that Jira cannot capture:

  • Escalations from customers or stakeholders
  • Verbal feedback from leadership or stand-ups
  • Decisions made outside the ticketing system
  • Context about why work slowed or accelerated

Daily insights are saved immediately with no AI involvement. For weekly and account reports, clicking Refresh Summary after editing insights shows a side-by-side preview before you commit the change.

Glossary for Non-Technical Readers

Jira
Project management software where teams track their work tickets
Ticket
A single work item (bug fix, feature, task) in Jira
Blocked
A ticket that can't proceed because it's waiting for something (approval, other team, etc.)
Stale
A ticket that's been "In Progress" but hasn't had any updates for 3+ days
Throughput
Number of tickets completed in a time period (higher = more productive)
Health Score
Green/Amber/Red indicator of project status based on rules
AI (Claude)
The artificial intelligence that writes the human-readable summaries
Hallucination
When AI invents information that isn't true (like "3 weeks" instead of "2 days")
Validation
Automated checking to catch AI mistakes before reports are saved
Deterministic
Based on rules and math, not guesses (reliable, repeatable)
BlockedTicketAnalyzer
Tool that mathematically calculates exact blocked durations from historical data
Lane Configuration
Board column groupings defined per project (e.g., "In Progress", "Blocked"). Determines which Jira statuses are considered active, done, or blocked for health scoring.
Shared Team Report
A special daily report for developers who contribute to multiple projects. The AI consolidates work from all projects into one unified summary for that developer.
Cache / forceRefresh
Reports are saved to the database after first generation. Subsequent requests return the cached version instantly. The "Queue your request" / forceRefresh option bypasses the cache to regenerate from current data.
Trend Context (3-week)
When generating a weekly report, the system also fetches the previous two weeks' metrics (avg tickets, throughput, blocked counts) and passes them to the AI so it can identify improving or worsening patterns.
TemporalValidator
Tool that scans AI output for invented time durations and flags suspicious claims
Team Performance
On-demand analytics module showing per-developer sprint delivery metrics, multi-sprint velocity bar charts, pipeline breakdown, and Kanban date-range history with period slicing.
Story Points (SP)
Effort estimation units assigned to Jira tickets. Team Performance uses SP Planned vs SP Done to measure delivery percentage per sprint.
Delivery %
Story points in Done + UAT + QA ÷ total story points assigned. UAT tickets count as V2-team-complete since development is finished.
Spillover
Tickets that were in the sprint at start but did not reach Done by sprint end — they carry over to the next sprint.
Period Slice
In Kanban Team History, the date range is divided into equal N-day windows (e.g. 15-day slices). Each slice shows how many tickets each developer delivered in that window.
